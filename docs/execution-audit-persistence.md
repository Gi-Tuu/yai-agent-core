# 执行审计的持久化边界（宿主接入指南）

> 对应 v0.25 B7 批次（任务书 P1-3）。YAI 提供**可靠的进程内审计契约**；
> 持久化存储由宿主负责。本文写清两者之间的边界与宿主侧的正确姿势。

## 一、进程内哈希链能保证什么、不能保证什么

`ExecutionAudit` 为每次执行密封一条 `ExecutionReceipt`（status / call_id /
idempotency_key / error / duration / replayed / postcondition），并用上一条的
`receipt_hash` 串成哈希链。宿主导出事件后用 `verify_receipt_chain(receipts)`
即可发现任何篡改、抽走或换序。

**能保证**：进程存活期间，链上任何一条被改动都会被校验发现。

**不能保证**：
- 进程崩溃 / 重启后链条还在内存里——**导出是宿主的责任**；
- 链外的收据（异常携带的 `partial_events` 若宿主不消费就丢了）；
- "第一条 prev_hash 为空"是链的起点——**进程重启即重开一条新链**，
  跨进程的链衔接由宿主在持久化侧处理。

## 二、宿主持久化的正确姿势

1. **实时导出**：消费事件流时把 `receipt` 字段逐条落到自己的审计存储
   （数据库 / 追加日志），不要等任务结束再一次性收集；
2. **重启后的 unknown**：任务在重启时被打断的执行，其副作用状态未知——
   宿主应把这类条目标记为 `unknown`，靠工具自身的幂等键重放或人工核对，
   **不要**假定"重启 = 没发生"；
3. **防重复副作用**：对声明了幂等键的调用，重放由内核缓存处理（同 key 同参数
   才命中，且权限收紧仍会拒绝）；跨进程的幂等去重需要宿主在自己的存储上做；
4. **后置条件检查失败**：检查抛错只保持 `unknown`（verdict=error），内核
   绝不替宿主猜"到底发生了没有"——宿主侧应把 error 的后置条件当人工工单。

## 三、敏感信息边界

- 收据**不含**参数与结果正文：`error` 在密封前经 `event_error` 治理脱敏；
- 事件流里的 `arguments` 是**独立的脱敏副本**（按 `governance.sensitive`
  声明，未声明即不脱敏——这是契约不是缺陷）；
- 宿主把事件写日志时，按自己声明的 `sensitive` 路径再过一遍自己的日志脱敏，
  双保险的职责划分：内核管事件形状，宿主管自己的存储。

## 四、关联关系

`call_id`（模型的工具调用 id）、组合步骤 id（`call_id:步骤序号`）、`run_id`
（sidecar）是三条既有线索。会话 ID 属于宿主：宿主持久化时把自己的会话 ID
与 `run_id`/`call_id` 一起落库即可建立关联，内核不需要知道会话概念。
