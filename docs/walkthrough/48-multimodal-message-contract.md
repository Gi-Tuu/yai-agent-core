# 逐行讲解 48 · 多模态消息契约：让 Agent 能"看见"，且不静默丢

> 之前内核的消息契约是**纯文本**（`ChatMessage.content: str`）。这一篇把它扩成
> **可选的多模态**：`ChatMessage.parts`。三条底线贯穿全文：
> **默认行为逐字不变**、**图片字节不落盘**、**看不到就明说看不到**。

## 0. 为什么是"可选字段"而不是"换掉 content"

直接把 `content` 改成 `str | list` 会一次性掀翻：所有构造点、所有持久化、所有
消费方（提示词拼装、摘要渲染、SQLite 落库、两家模型适配器）都要跟着改，
而**收益只是让宿主能塞张图**。所以选了一个可回退的形状：

```python
@dataclass
class ChatMessage:
    role: Role
    content: str = ""                       # 老字段，一字未动
    parts: list[ContentPart] | None = None  # 新字段，None = 纯文本消息
```

`parts is None` 时，`to_llm_dict()` 的输出与过去**逐字节相同**（有测试钉住）。
宿主想用多模态就填 `parts`，不想用就什么都不做——**不强制、不劝退**。

## 1. 三种片段，两种"看得见/看不见"

```python
TextPart(text="...")                    # 文本片段
ImagePart(media_type=..., data=..., ref=...)   # 图片：内联 or 引用，二选一
ResourcePart(uri=..., media_type=..., name=...) # 资源引用（宿主签发）
```

`ImagePart` 的两条路径，差别很大：

| 字段 | 含义 | 模型能看到吗 |
|---|---|---|
| `data` | 宿主在信任边界上解析好的内联 base64 | **能**（真的被翻译成图片块） |
| `ref` | 宿主签发的引用（`res://host/42`） | **不能** |

为什么 `ref` 不能被内核"顺手取一下"？因为**取**就是一次外部访问：
要有授权、要防 SSRF、要管生命周期。内核不替宿主做这个决定，只负责
"如实告诉模型这里有个引用，而它看不到内容"：

```
[图片引用：res://host/42 —— 未内联，模型看不到这张图]
```

**宁可明说不可见，也不要静默丢**。静默丢的后果是：模型在缺资料的情况下
照常回答，看起来成功、其实答错——而宿主根本不知道发生过这事。
`ResourcePart` 同理：它只说"有这么个资源，内容由宿主提供"。

## 2. 出站形态：内容数组（各家的原生形态）

`to_llm_dict()` 在有片段时输出 **OpenAI 兼容的内容数组**：

```python
{"role": "user", "content": [
    {"type": "text", "text": "看这张图"},
    {"type": "image_url", "image_url": {"url": "data:image/png;base64,..."}},
]}
```

选它有两个理由：① 这本来就是 OpenAI 兼容后端的**原生形态**，
`OpenAICompatProvider` 直通即可，零改动；② 内核内部消息形态本来就是
"OpenAI 兼容 dict"（`llm_messages()` 的既有口径），不引入第二套内部协议。

`AnthropicProvider` 需要**翻译**（Claude 的图片块形状不同）：

```
{"type": "image_url", "image_url": {"url": "data:image/png;base64,XXX"}}
        ↓
{"type": "image", "source": {"type": "base64", "media_type": "image/png", "data": "XXX"}}
```

这一步之前是**压平成空文本**的——图片确实看不见。现在图片真的到了模型面前。

## 3. 降级：给不支持多模态的模型 / 摘要用

`parts_to_text(parts)` 把片段渲染成纯文本，两处用它：

1. **上下文摘要**（`render_for_summary`）：摘要器是纯文本模型，图片引用会被渲染成
   占位文本一起进摘要——否则"用户发来截图，结论是…"这条事实会凭空消失；
2. **降级路径**：宿主要接一个只吃纯文本的后端时，自己调它即可。

## 4. 落盘：只存引用，不存图片字节

`history` 表新增 `parts` 列（schema v2 → v3），存的是**引用形态**：

```json
[{"type": "image", "media_type": "image/png", "ref": "res://host/42"},
 {"type": "resource", "uri": "file://secret/report.pdf", "name": "report.pdf"}]
```

**图片字节不落盘**。理由很直接：历史是长期驻留的，把 base64 图片塞进去，
过几个月就是库里一堆没人看得懂的二进制。代价是**读回的图片没有内联数据**，
于是它会渲染成"模型看不到"的占位——这是刻意的取舍，**取舍本身要写在脸上**，
而不是让人以为"图还在"。

迁移是**逐级**的（v1 → v2 → v3），并且照顾两种老库：表根本不存在（手工造过的
残缺库）→ 按 v3 建表；表在但缺列 → `ALTER TABLE` 补列。两种都不丢数据。

## 5. 三条不变量（写进测试）

1. `parts is None` 的消息，`to_llm_dict()` 与旧版**逐字节相同**；
2. 落盘后的库里**搜不到图片字节**；
3. 不可见的图片/资源，在文本渲染里**必须带着"看不到"的说明**。
