# YAI Agent Core v0.11.0

> 发布日期：2026-10-16 · 范围：`v0.10.0` 之后的 6 个 PR（#60–#65）· 许可证：MIT
> 本页是 GitHub Release 正文源稿；逐条变更清单以 [`CHANGELOG.md`](https://github.com/Gi-Tuu/yai-agent-core/blob/main/CHANGELOG.md) 的 `[v0.11.0]` 小节为准。

**这一版的主线只有一件事：把"治理"从外部契约里拿回来，变成内核自己的东西。** 上一版我们接了 ACC（一个外部的能力声明契约），于是出现一个别扭的现状——宿主只想说一句"退款超过 1000 要人确认"，却得先学会一个外部协议，或者自己手写一个判定函数（函数进不了能力清单、跨不了语言，而且每家都得把"超过"这个词重新实现一遍）。这一版把这套判定整块搬进内核，外部协议反过来降级成"翻译器"。

**没有破坏性变更**：`approval` 不声明就没有任何行为，`filesystem_gate` 由宿主自己挂载，未治理工具的 `TOOL_CALL` / `PERMISSION_ASKED` 事件形状逐字不变，`import` 方式与 v0.10.0 一致。只有一处**审批话术**变了，见下面最后一节。

---

## 参数级审批现在是原生的：写数据，不用写函数

```python
from yai_core import ApprovalPolicy, ApprovalRule, ToolGovernance, build_spec

spec = build_spec(refund_order)          # 普通 Python 函数，零胶水
spec.governance = ToolGovernance(
    approval=ApprovalPolicy(
        prompt="退款 {amount} 元，确认吗？",
        when=(ApprovalRule("amount", ">", 1000, label="金额超限"),),
    )
)
```

判定语义住在 `yai_core.policy.approval`（纯函数、零依赖），三条不可让步：

- **严格 JSON 值比较**：`"1000" != 1000`、`True != 1`。不做任何隐式转换——静默转换等于给"参数写成字符串的那次调用"开一条绕过金额门槛的路。
- **判不出来就失败关闭**：算子不认识、条件路径没在绑定 schema 里声明、连 schema 都没绑、数值比较遇到 NaN/Infinity、`contains` 遇到标量 —— 一律判**拒绝执行**，绝不"当条件没命中"放行。
- **只能抬不能放**：审批要求能把权限策略的 ALLOW 抬成人工确认，但**永远压不过 DENY**。放行与否始终归宿主的 `PermissionPolicy`。

因为它是**数据**，所以随能力清单（manifest）一起走：导出、跨进程、换语言，导入端不需要任何外部协议就能恢复这份强制。入站逐字段严校验——未知字段、非法算子、类型不对一律**拒绝加载**，因为清单里出现"内核不认识的强制项"绝不能被静默忽略。

同一个工具既挂了 `gate`（函数）又写了 `approval`（数据）时，执行器**取更严的那个合并**，两边的理由都进审批事件、只问一次人。"有 gate 就当 approval 不存在"等于声明了的保护内核没做，这是这一版拒绝的设计取舍。

## 顺手挖出来两个真缺陷（如果你被"合法调用被拒"困扰过，原因在这里）

1. **`from __future__ import annotations` 会让工具 schema 骗人。** 函数内省过去只认"注解对象"，而 PEP 563 下注解全是字符串：`amount: float` 被看成 `"float"`、查表不中，于是**所有参数一律退化成 JSON `string`**。表面看只是描述难看，实际后果是审批按绑定 schema 校验入参时"期望 string、实到 number"——每一次合法调用都被拒在业务操作之前。现在 `build_spec` 先走 `get_type_hints` 解析字符串注解，解不开才退回兜底。**为什么一直没被发现**：既有测试都把正确的 schema 手交给闸，绕过了内省这一步。
2. **能力清单导出会悄悄丢掉审批阈值。** 手写 `ApprovalRule("amount", ">", 1000)` 时 `has_value` 默认是 `False`，而导出规则是"没给值就不写 `value` 键"——导出的清单里阈值消失，导入端就成了"`>` 没有可比的值"，于是**每次调用都被拒**。`ApprovalRule.__post_init__` 现在见到非 None 的值就把 `has_value` 补上：忘填一个布尔只是省事，不该因此改变语义。

另外补了一个字段级隐患：`ToolGovernance` 的新字段排在 `gate` **之后**，因为老宿主有 `ToolGovernance(sensitive, audit_sensitive, acc, my_gate)` 这种位置写法——插在中间不会报错，只会把绑好的闸门静默挪走、`gate` 变 None。有测试钉住。

## ACC 层降级为翻译器，判定只剩一份

`integrations/acc` 从 299 行的"决策层"瘦成 118 行：只保留 ACC 特有的三个派生量（能力可达、有效风险、审计宽口径提示）与一个 `to_approval_policy` 翻译器；`AccApprovalCondition` 直接成为 `ApprovalRule` 的别名（九个算子一字不差，再养一个同构数据类只会制造"两个模型谁说了算"）。

- **证据形式**：同一份声明、同一个入参，走 ACC 路径与走原生路径的 decision 与 reason 必须一字不差（12 组参数化用例，含全部失败关闭组合）。
- **依赖方向**：新增一条子进程探针——只 import 内核模块时，`sys.modules` 里不许出现任何 `yai_core.integrations`。
- **对外口径不变**：仍然只声称 *Implements the ACC v1 OpenAPI Binding Parser Profile*，不写"ACC certified"（规范明令禁止），`timeout_ms` / `rate_limit` 仍未映射到执行器，限制清单照实列。

## 审批人终于看得见"这次到底动哪个资源"

- **`risk` / `scope` / `target` 进事件**：这三个值 `GateDecision` 早就算出来了，但执行器只用其中"拒不拒、问不问"，其余**算出来就扔**。现在它们随 `PERMISSION_ASKED`（让人判断该不该批）与 `TOOL_CALL`（事后按风险检索）一起发出。空值不写键，未治理工具的事件形状逐字不变。
- **资源作用域闸 `filesystem_gate`**：文件系统的两道路径闸只管"出不出根目录"，管不了"根目录内的哪一块"，而宿主想说的恰恰是"只能碰 `notes/`"。按模型写来的原始字符串匹配白名单是假的——`notes/a.txt`、`./notes/a.txt`、`notes//a.txt`、`notes/./a.txt` 是同一目标的四种写法，而且人工审批看到的正是这个原始串。新闸用**与 handler 完全相同的** `normalize_relative` 规范化，所以"批准目标 == 执行目标"是构造上成立、不靠约定；`write=True` 配空白名单 = 拒绝一切写。
- 三条边界照实写：前缀匹配是**字面**的（`NOTES/` 在 `notes/` 下会被误拒，宁可误拒）；它**不替代**逐段拦符号链接与 realpath 复核（批准与写入之间被换成链接仍然失败关闭）；它**不做授权**（策略 DENY 永远优先）。

## 一处话术变化（依赖日志文案做匹配的宿主请注意）

审批结论的 `reason` 不再输出 `approval.required` / `approval.when` 这类协议术语，改为内核中文口径："该能力要求每次调用都人工确认（条件规则不得削弱它）"、"命中审批条件：金额超限"。**判定语义逐条不变**，官方向量与全部既有测试的 decision 断言仍然全绿；原本有两条测试钉的是术语字符串而不是行为，已改为钉行为。

## 上游一致性语料不再随包分发

`tests/fixtures/acc/` 的 26 条 Apache-2.0 官方向量此前随 sdist 一起发布——**合规**（出处、许可证、逐字节哈希都在），但那是别人的测试数据集，我们没有对外分发它的必要。现在 sdist 排除该目录，缺文件时相关测试整模块 `skip` 而不是报错。源码仓库与 CI 仍然全量跑这 26 条。实测两条（对 `0.11.0` 构建产物）：`fixtures/acc` 命中 0、`tests/` 仍有 93 个文件；语料一致性测试本身在本地解包 sdist 后得 `1 skipped` 而不是报错。

## 内核边界没动

- 内核 **93 个源文件 / 13 992 行**，`dependencies = []` 仍然为空（第三方只进可选 extras 并懒加载）
- **10 个可替换 SPI 契约**、**19 类结构化事件**（单一事件出口，禁止静默决策）
- **1 327 项自动化测试通过 / 5 项环境跳过**，行覆盖率 **96%**（CI 硬门禁 90），全部离线、不需要 API Key
- CI：Linux py3.11 / 3.12 / 3.13 + Windows py3.13 四矩阵，CodeQL、Scorecard、模糊测试、路由基准与端到端评测
- 路由自校准基准（本版 CI 产物实测）：**末段成功率 89.6% vs 规则基线 73.3%（+16.3pp）**，Oracle 100%，误澄清率 4.2%
- 9 个宿主目录（8 个可运行宿主示例）+ 一个原生桌面产品壳

## 诚实边界（不写进卖点的那些）

- 不做 MCP Server、不做多智能体、不内置代码执行器、不内置界面、不做向量长期记忆。
- 未声明的参数**不会**被脱敏；`approval` 未声明的条件路径**不会**被猜——安全语义只来自声明，猜出来的东西不能当安全承诺。
- 审批只看参数，不看"这个主体对这个资源到底有没有权限"：跨租户与按主体的资源授权仍归宿主（`filesystem_gate` 给的是作用域闸，不是授权模型）。
- 组合工具自己声明的审批会问一次，但仍然**不替组合名跑权限策略**（组合名是黑盒，权限精确落到每一步）。
- 风险等级、`scope`、`target` 都是**描述性**字段：内核不按风险自动升降档。
- 单人项目，社区数据如实：Star 3、外部贡献者 0。

## 安装

```bash
pip install yai-agent-core            # PyPI（本版本发布后即为 0.11.0）
pip install "yai-agent-core[llm]"     # 加 OpenAI 兼容后端
pip install "yai-agent-core[anthropic]"
uv add yai-agent-core
```

每个发布产物带 SLSA 构建证明、cosign keyless 签名与校验和；构建与发布由 `publish.yml` 在 tag 推送时自动完成。
