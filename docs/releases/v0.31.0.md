# v0.31.0 — 长期记忆 10k

v0.31.0 把长期记忆从"1,000 条都吃力"推到 **10,000 条可跑通**：批量写入把 N 次全量落盘合并成
一次，倒排索引改为增量维护，去重路径加 token 缓存与共享 token 预筛。内核依赖与公开契约不变。

## 重点

- **`remember_many()` / `batch()`**：批量写入期间只标脏，退出最外层时统一落盘一次；
  内存语义（去重合并、容量淘汰、倒排维护）与逐条写入完全一致。
- **增量倒排索引**：新增 / 合并 / 删除 / 容量淘汰只改动相关 posting，
  不再在每次写入后整表重建（旧实现的主要 CPU 开销）。
- **去重路径**：`contains()` 改 O(1) id 集合；token 集按 note 缓存；按"共享 token 数"预筛
  （合并阈值 0.92 可推出共享 token 必 ≥0.8×|query|，预筛不改变合并结果）。
- **基准**：`benchmarks/memory/scale_bench.py` 支持批量构建与 `--single` 对照。

| 规模 | 构建 | 检索 P50 | 检索 P95 | 更新 10% |
|---:|---:|---:|---:|---:|
| 1,000 | **0.59 s**（旧 79.8 s） | 1.0 ms | 43 ms | 76 ms |
| 5,000 | 10.8 s | 7.4 ms | 106 ms | 1.58 s |
| 10,000 | **45.4 s** | **17.6 ms** | 116 ms | 6.44 s |

## 升级指引

- 无 breaking：新增 API，默认单条 `remember` 行为不变（仍每条落盘，保证单写持久性）。
- 批量导入请用 `remember_many()` / `with vault.batch():`，否则 10k 规模仍会很慢。

## 验证

- 新增 `tests/test_memory_batch.py`（7 例：批量等价、单次落盘、增量索引与重建一致、
  批量内去重、2k 构建重载、异常仍落盘、基准脚本）；全量门禁通过。
- 旧测试 `test_lex_index_lazily_built_*` 已更新为"懒构建 + 增量一致"的新口径。

## 明确边界

- 45.4 s 是"一次性建库"量级，不是交互级批量导入；逐条 `remember` 在 10k 下仍慢。
- 语义通道（embedding）**未在 10k 规模基准化**；超大/高频场景仍建议 `SqliteStore` 或宿主向量库。
- 10k 数字来自本机 CPU 纯词法通道，不代表生产负载。

完整逐条变更见 [`CHANGELOG.md`](https://github.com/Gi-Tuu/yai-agent-core/blob/main/CHANGELOG.md)。
